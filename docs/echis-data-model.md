# eCHIS FHIR Dataset Model

Status: Implemented (dev-server-aligned data model)

Issue: tracked against issue #18 (benchmark-lab epic), extending spec 008 and spec 010.

Decision: `scripts/echis_seed.rb` generates households, staff, and visit history in the shape the eCHIS dev server (`https://echisv3.intellisoftkenya.com/fhir`) actually holds, driven by that server's own Questionnaires and PlanDefinitions, so app-server benchmarks exercise realistic payloads, references, tags, and sync queries.

## Context

Spec 008 and spec 010 shaped the dataset from a planning-level model: generic LOINC vitals, SNOMED conditions, a one-item placeholder `QuestionnaireResponse`, and a synthetic facility/sub-region/region hierarchy tagged with a repository-local catchment system. The dev server looks different. Households are `Group`s managed by a CHV `PractitionerRole` inside a Kenya administrative `Location` tree. Every patient-data record carries a `supervision-location` sync tag, and care is recorded by walking real forms (the under-5 assessment alone has 105 items), with `Observation`, `DetectedIssue`, and `Task` records derived from the responses.

This is a clean break from the spec 008/010 resource shapes. What stayed stable:

- **CLI:** the flags and their meanings (`--households`, `--individuals-per-household`, `--seed`, `--shard-index`/`--shard-count`, `--metadata-only`, `--include-specimen`, ...).
- **Metadata:** the `echis` metadata schema that `scripts/merge_seed_shards.rb` and `scripts/publish_results.rb` read.
- **Sharding:** contiguous household ranges, deterministic ids, and idempotent `PUT`s.
- **Ids:** `Group`, `Patient`, `RelatedPerson`, CHV `PractitionerRole`/`Practitioner`, `CareTeam`, and `Organization` keep their formats. `CareTeam`, `RelatedPerson`, and `Condition` are kept because they are expected on the dev server soon, even though it has none today.

## Reference content snapshot

`benchmarks/echis/content/echis-content.json` is a verbatim copy of the dev server's reference content, with server `meta` stripped:

| Type | Count | Use |
| --- | --- | --- |
| `Questionnaire` | 21 | Every visit's `QuestionnaireResponse` is generated by walking one of these |
| `PlanDefinition` | 34 | 15 workflow definitions linked from visits; 19 decision rules whose ids are `DetectedIssue` codes |
| `ActivityDefinition` | 7 | `Task.instantiatesCanonical` targets |
| `Location` | 48 | Kenya (country) and its 47 counties; everything below a county is generated |

The generator `PUT`s this content before any household data, from every shard, because household data references the county `Location`s. It is counted in `resource_counts` by shard 0 only, so merged metadata counts it once. Refresh the snapshot when the dev server's forms change:

```sh
scripts/snapshot_echis_content.rb   # defaults to the dev server and the committed path
```

Generated responses pick answers from each item's own `answerOption` list and honour `enableWhen`, so a refreshed form changes the generated data without code changes. In-cluster seed Jobs receive the snapshot gzipped in the scripts ConfigMap (`--content /scripts/echis-content.json.gz`), because the raw file would exceed `kubectl apply`'s 262KB last-applied-configuration annotation.

## Catchment hierarchy and staff

Sized to Kenya's community health strategy. Every index is integer division from the global household index, so each shard derives the same ids independently:

| Level | Size | Id format | Real-world check at T5 (10M households) |
| --- | --- | --- | --- |
| CHV (Community Health Promoter) | 100 households | `echis-chw%06d` (role), `echis-pr%06d` (practitioner), `echis-ct%06d` (care team) | 100,000 CHVs |
| Community Health Unit (`unit`) | 10 CHVs | `echis-loc-chu%06d`; CHA `echis-cha%06d` / `echis-pr-cha%06d` | 10,000 units |
| Link facility | 2 units | `echis-loc-fac%06d` | 5,000 facilities |
| Ward | 3 facilities | `echis-loc-ward%06d` | ~1,667 wards (Kenya: ~1,450) |
| Sub-county | 5 wards | `echis-loc-sub%06d` | ~333 sub-counties (Kenya: ~300) |
| County | round-robin over the snapshot's 47 counties | snapshot ids | 47 |

Each unit contributes its `Location` chain plus one CHA. Each CHV contributes a `Practitioner`, a `PractitionerRole` (located at the unit), and a `CareTeam` whose participants are the CHV and CHA, managed by the single `Organization` (`echis-org000001`).

**Cross-shard redundancy:** a unit or CHV catchment that straddles a shard boundary is `PUT` once by each shard touching it. That is safe (identical content), but it can inflate the *reported* `Location`/`Practitioner`/`PractitionerRole`/`CareTeam`/`Organization` counts in merged metadata. Household-owned types are generated by exactly one shard.

## Households

- **Size:** cycles `N`, `N+1`, `N-1` around `--individuals-per-household N` (for `N >= 2`), so rosters vary like the dev server's while individual indices stay contiguous. Individuals for `H` households = `H*N + (1 if H mod 3 == 2)`.
- **Roster:** a head (22-70), usually a spouse, then children. 45% of children are under five, giving ~15% under-fives overall (Kenya: ~13-14%). Occasionally an elderly parent completes a household of 4 or more. Names are Kenyan; dates are relative to a fixed `2026-09-01`, never the clock.
- **`Group`** `echis-hh%08d`: `type: person`, `actual: true`, `name` (`<Family> Household`), `managingEntity` is the CHV role, and each `member[]` is a `Patient` reference with display and `period.start` (the registration date).
- **`Patient`** `echis-p%08d`: official name, phone for adults, gender, `birthDate`, and a home address (village, ward, sub-county, county, `KE`). Non-heads also get a `contact.relationship` to the head. `generalPractitioner` is the CHV role; `deceasedDateTime` is set when a death report exists.
- **`RelatedPerson`** `echis-rp%08d`: one per non-head member. `patient` is the member; `relationship` is the head's role relative to them (a child's head is `PRN`); name and phone are the head's.
- **Household registration:** a `QuestionnaireResponse` (`echis-qr-hh%08d`) for the `household-registration` form, with subject the `Group` and no `Encounter`, matching the dev server. Its answers include the real roster in the repeating `household-members` group. Three WASH `Observation`s (water source, sanitation facility, handwashing) have subject the `Group` and are `derivedFrom` the response.

Every generated patient-data resource (`Group`, `Patient`, `RelatedPerson`, `CareTeam`, `PractitionerRole`, `QuestionnaireResponse`, `Encounter`, `Observation`, `DetectedIssue`, `Task`, `Condition`, `Specimen`) carries the unit's `supervision-location` tag.

## Visits

Each service visit walks one snapshot `Questionnaire` for one person and writes the same records the app writes:

- **`Encounter`:** `class` `FLD`/Field, status `finished`, with an `instantiates-plan-definition` extension naming the workflow.
- **`QuestionnaireResponse`:** `questionnaire` is the form's canonical URL, with `lastLaunched` and plan-definition extensions, `authored`, and every enabled item including display text (`{{name}}` rendered).
- **`Observation`s:** one per answered item the form marks `observation-extract`. Code comes from the item and value from the answer, typed as `valueCodeableConcept`, `valueInteger`, `valueQuantity` (Cel for temperature), or `valueBoolean`. Each is `derivedFrom` the response.

Visit mix per individual. Answer prevalence is tuned in `ANSWER_PROFILES`: danger signs are rare, availability is common, and multi-option "none" answers dominate.

| Visit | Who | Rate | Adds |
| --- | --- | --- | --- |
| Under 5 Assessment | every child under 5 | 100% | ~4-16 extracted observations; `DetectedIssue`s per decision rule; malaria `Condition` on a positive RDT; `Specimen` per RDT with `--include-specimen` |
| Immunization Service | children under 5 | 70% under 2 years, 30% otherwise | up to 3 extracted observations; milestone and defaulter alerts; Defaulter Follow Up visit for half of not-up-to-date children |
| Pregnancy Screening and Registration, then Pregnancy Home Service | female head/spouse aged 15-49 | 8% (home service for 70% of those) | pregnancy `Condition`; routine ANC `Task` |
| Mother and Newborn PNC Home Service | mothers with an infant under 6 months | 60% | PNC danger-sign alert |
| Diabetes Service | age 35+ | 5% | type 2 diabetes `Condition` |
| TB Service | age 15+ | 0.6% | tuberculosis `Condition` |
| Death Report | age 60+ | 1.5% | `Patient.deceasedDateTime` |

**Decision rules:** these follow the snapshot's decision-support PlanDefinitions. Under-5 rules cover fast breathing for age, high and low temperature, diarrhoea over 14 days, blood in stool, chest in-drawing, convulsions, inability to drink or feed, vomiting everything, unusual sleepiness, MUAC red and yellow, swelling of both feet, and negative malaria test with fever. Any core danger sign also raises `under-5-any-core-danger-sign-refer-immediately-alert`.

Each `DetectedIssue` (`status: preliminary`, `severity: high`) is tied to the rule's PlanDefinition, `author` is the CHV role, `implicated` is the response, and `evidence` is the triggering observation. A visit that raises any alert gets an urgent `follow-up-on-referral` `Task` owned by the CHV. Half of those are `completed` with a Referral Follow Up visit; the rest stay `requested`.

**Ids:** visit resources use `echis-<kind>-<visit><individual%08d>`, e.g. `echis-qr-u500000042`, `echis-obs-u500000042-03`, `echis-di-u500000042-00`, `echis-task-refu500000042`.

## Determinism

All randomness is SplitMix64 keyed on `(--seed, person/household/unit index, purpose)`, so any shard reproduces byte-identical bundles (asserted by `test/echis_seed_test.rb`). Changing `--seed` changes demographics, visit mix, and answers, but not household or individual counts.

## Cardinality

With `--individuals-per-household 3 --seed 12345`, the dataset averages ~16.4 records per household. At T2 shape (33,333 households), `Observation` is ~6.8 per household, `QuestionnaireResponse` ~2.0, `Encounter` ~1.0, `DetectedIssue` ~0.2, and `Task` ~0.2. Payloads are larger than before: responses average ~5.6KB, and an under-5 assessment reaches ~13.5KB. Exact per-tier totals are in `docs/echis-benchmark-tiers.md`.

## Benchmark workload alignment

`benchmarks/k6/lib/fhir_benchmark.js`'s `echis` workload writes the same shapes, with operation names and weights unchanged. Its self-contained writes are tagged with a per-shard pseudo-unit (`echis-loc-chu-k6-s<shard>`) so they never enter a seeded unit's sync scope.

Setting `ECHIS_SEEDED_HOUSEHOLDS` to the seeded `--households` adds the sync-engine calls from the "OHS FHIR Sync -- API Call Inventory & Performance Simulation Baseline" document against the seeded data:

- **`sync_download_read`:** tag-scoped `_sort=_lastUpdated` pulls with `_lastUpdated=gt` floors, following `next` links.
- **`patient_everything_read`:** `Patient/{id}/$everything`, with or without `_since`.
- **`household_scoped_read`:** `Group?_id=a,b,c&_include=Group:member`.
- **`sync_upload_write`:** a transaction with `PUT` visit resources plus a JSON Patch to a seeded `Patient`.

## Verification

`scripts/verify_echis_catchment_data.rb --fhir-base-url URL [--unit-id echis-loc-chu000000]` replays one unit's sync calls against a loaded server. It checks the six-level `Location` chain, tag-scoped pulls for `Group`/`Patient`/`Task`/`QuestionnaireResponse`/`Encounter`/`Observation`, a roster `_include` read with member `$everything`, the CHV role-to-practitioner chain, and that a generated response's `questionnaire` canonical resolves.
